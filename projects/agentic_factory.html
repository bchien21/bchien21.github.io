Multi-Agent Orchestration of a Factory Production Line*

*For confidentiality, video demonstrations and code for this project cannot yet be made public.

Project Summary/Accomplishments (TL;DR)

  • Built a generative AI stack for LLM-driven orchestration of a factory testbed; deployed agents to orchestrate physical machines via MCP tool-calling, demonstrating autonomous coordination for versatile workflows.
  • Developed specialized, vision-based tools for agents to recover from faults without human intervention.
  • Quantized open-source LLMs to fit memory constraints of an NVIDIA Jetson for local deployment, achieving a reduction of over 50\% in inference time compared to API-based models.
  • Implemented a networked backend with REST APIs and SSE to asynchronously stream real-time agent reasoning outputs to a client-facing dashboard.
  • Development Tools:
    • LangChain: Framework for building LLM-powered agents.
    • Agent2Agent (A2A) Protocol: Protocol for inter-agent communication.
    • Model Context Protocol (MCP): Protocol for agent tool-calling.
    • llama.cpp: Library for local LLM/VLM quantization.

AI Agent Development

Software Architecture: Reasoning + Action (ReAct) Loop

  • At each iteration of the agentic loop, the AI agent chooses to do only one of the following:
    • Send a message to another agent, via the A2A protocol.
    • Check for a message from another agent.
    • Select an MCP tool from its available set of tools, and invoke it for machine control.
  • All agents follow this ReAct-based architecture, allowing for seamless additions of new agents to the stack.
  • What differs between agents are the following:
    • System Prompt: An initial prompt which informs the agent about its machine, its set of tools, and its fellow agents.
    • MCP Tools: Software functions for physically orchestrating a machine.
    • User Query: A prompt which informs the agent of the task it must perform.
  • This design philosophy maximizes autonomy/flexibility. All agents run asynchronously, but can communicate to perform synchronous tasks.

Highest-Level Orchestrator Agent

  • At the highest level of this agentic pipeline is an orchestrator agent, which is in charge of managing the lower-level agents which perform direct machine control.
  • This orchestrator directly receives a client request. Then, it uses that request to delegate a detailed prompt/task for each lower-level agent to complete. This task is essentially the user query which kicks off the lifecycle of the agent. After delegation, the orchestrator and the rest of the agents run asynchronously. The orchestrator constantly monitors the status of each lower-level agent, checking for completion.

Research Platform: Fischertechnik Factory Testbed

Factory Machines (Miniature Models)

Production Line Arrangement

  • A company named Fischertechnik develops miniature models of factory machines for automation training. Traditionally controlled via PLC logic, these machines are now orchestrated by the AI agents.
  • These machines are arranged in the following formation to simulate a production line, where material from the beginning of the line is moved to be stored into the warehouse at the end of the line. As shown in the diagram, each component of the line is managed by an agent.

MCP Tool Development For Low-Level Control

  • Each machine's motors connect to the I/O ports of a PLC rack via a signal wire. The PLC exposes the address of each I/O port over Ethernet. With the OPC-UA library, MCP tools can drive any address to high or low, fully energizing a motor to induce movement or stopping it completely.
  • This eliminates any need for PLC-side logic.
  • Each MCP tool strictly performs a single action, adhering to a design philosophy of minimal logic. Examples include:
    • Drive the conveyor belt forward.
    • Have the robot pick up material from the input bay.

Vision-Based MCP Tools for Error Recovery

  • To validate the state of the production line, specialized vision-based tools were developed for agents to read data from RGB cameras. Two industrial cameras have overhead views of the line, while both robots have USB cameras attached to their end-effectors.
  • Example Error Recovery Workflows:
    • The conveyor agent expects to have sorted a product of some classification. However, the agent realizes with the overhead camera that this product is not present in the sorted section. So, the agent sends a message to the upstream 3-DOF robot agent to immediately retrieve another product of the same classification.
    • The 3-DOF robot agents realize, through their USB cameras, that they did not properly grip the product. So, the agent re-calls an MCP tool to retry this process.

Optimization: Model Quantization for Edge Deployment

  • For lower-complexity agents (Such as the conveyor agent), the reasoning capabilities of cloud models becomes a bottleneck.
  • A quantization pipeline via llama.cpp was developed to quantize local models for edge inference on an NVIDIA Jetson AGX Orin for edge inference. This pipeline proceeds as follows:
    • A raw model downloaded from Hugging Face contains files such as JSON configurations and safetensor weights.
    • A llama.cpp script "convert_hf_to_gguf.py" combines those files into a singular, unquantized 16-bit GGUF file, where "GGUF" is the model format necessary for llama.cpp to consume.
    • Then, a command-line utility as part of the llama.cpp project named "llama-quantize" is ran. This utility requires the 16-bit GGUF file and a desired quantization format, producing a new GGUF model with quantized weights.
  • The model chosen is Qwen3-30B-A3B-Instruct-2507. With 30 billion parameters, this model can handle the complexity of tasks requiring constant tool calls. Yet with only 3 billion active parameters, inference on a Jetson AGX Orin is rapid.
  • On average, inference takes 1-2 seconds. With previous API-based cloud inference, inference was 3-5 seconds. A reduction of over 50% in inference time was achieved.

Stakeholder-Facing Dashboard

  • For stakeholder demonstrations (and as a useful debugging tool), a dashboard with a FastAPI-based backend was built to visualize the reasoning output of each agent during production.
  • Every action performed by each agent (tool-calling, A2A messaging, or A2A inbox checking) is logged into this dashboard, alongside the reasoning process of the agent that led it to choose that action.
